# Blackline

Estimating and cost-control platform for NZ construction contractors. Read `ARCHITECTURE.md` first: it is the spec.

## Rules
- Money and quantities are decimal strings and `decimal.js` values. Never use JS floats for them. Round to cents with `cents()` (half-up).
- Calculation engines (`packages/engine`, `packages/tender`) are the only places totals are computed. They must give identical results on the client and the server.
- Offline work uses package checkout (`packages/checkout`), not a sync engine. A check-in is refused unless the lock is still held and the base version matches; refused changes are parked for a person to compare. Money is never merged silently.
- Issued tender revisions are frozen and can only be superseded.
- AI never computes totals. It drafts and flags; the estimator approves (QSi Pro rules 1-4).
- UI style: black, white and greys only, dense grids, square corners, no gradients.

## Commands
- `npm test` runs vitest across packages.
- `npx tsc -b packages/engine packages/checkout packages/tender` typechecks.

## Two engines, two rounding models (do not mix them)
- `packages/engine` is **QSi** (small contractors): rick284/blackline-estimating-standalone. Each resource line is rounded to the cent; risk rows are % of categories; overhead is % of cost base; sell = cost / (1 - margin).
- `packages/tender` is **TQSi / QSi Pro**: rick284/tender-estimating-platform (`engine/tender_engine`). It carries full precision and **never rounds inside the chain**, as the Master Estimate Workbook does (it displays 2dp but keeps full precision). Round only for display and reconciliation with `cents()`.
- The TQSi pricing stack lives in one place, `priceStack` in `commercial.ts` (overhead, profit, bonds, finance). Own-works tender, consolidated package and client schedule all use it. Do not re-derive it elsewhere (a QSi Pro review found exactly that bug).

## Server and data model (`packages/server`)
- Fastify 5 API over Postgres SQL. Schema in `src/migrations/001_init.sql`; run by `migrate()`. Dev and tests use PGlite (a real in-process Postgres); production passes the same SQL to a `pg` pool (`openPg`) behind the `Db` interface in `db.ts`.
- **Every tenant table has `org_id`, and child tables reference their parent on `(id, org_id)`**, so a row can never point at another company's data (tested at the database level). Every repository call takes a `Ctx` and filters by `ctx.orgId`. Another company's id gets the same 404 as an id that does not exist.
- **Checkout is by package, and a package is a QS section** (plus Rate Library, Commercial, Subcontract Packages, Risk and Reserve, Register/Quotes/Scope, Programme and Schedule, Job Settings). `tender/src/packaging.ts` splits a `TenderInputs` into packages and assembles it back; the round trip is exact (tested on Hobsonville). Records are `{kind, seq?, body}`; money is a decimal string inside jsonb, never a float.
- Check-in runs `@blackline/checkout` as the single authority: the repo loads the package's lock into its Store, asks it, then makes the database match. One transaction per call, `select ... for update` on the package row. A refused check-in is applied nowhere and parked in `parked_changes` for a manager to compare; a manager can break a lock; add-only records need no lock (first write wins).
- Roles: viewer (read) < estimator (checkout, check-in, add-only records, create jobs) < manager (break locks, import, resolve parked, add estimators/viewers) < owner (adds managers).
- Auth: scrypt password hashes, opaque session tokens stored as SHA-256, 14-day sessions, minimum password 10 characters. Sign-in and sign-up are rate-limited in hosted mode (in memory, one process). Not done: password reset by email (the admin tool resets it), email verification, session listing.
- **Hosting** (guide: `docs/HOSTING.md`; nothing is deployed yet): one container (`Dockerfile`, untested: no Docker here) runs the API and serves the built web app (`src/web.ts`: files from `WEB_DIR`, any other GET is the app, `/assets` cached a year; the server strips an `/api` prefix itself via `rewriteUrl`, as the dev proxy does) with a Postgres from `DATABASE_URL` (`openPg`: tested by `npm run test:pg`, the server suite through the wire protocol on PGlite's socket server; two tests skip there because that stand-in resets the connection on an SQL error). `main.ts` is driven by env (`.env.example`): `NODE_ENV=production` needs `DATABASE_URL`, refuses `SEED_DEMO`, turns on rate limits (`ratelimit.ts`; `loginPerEmail` 8, `loginPerIp` 40 per 15 min, `registerPerIp` 5 per hour), security headers (CSP `script-src 'self'`, no framing, HSTS over https) and `REGISTRATION=first|closed|open` (hosted default `first`: `GET /auth/status` says whether the sign-in screen shows "New company"). `AppOptions` in `app.ts` are all off by default, so tests and dev are unchanged. `/health` also checks the database (503 when it can't). `migrate()` takes a Postgres advisory lock so several servers can start together; a unique-violation (23505) from two overlapping requests is a 409 `conflict`, deadlock/serialisation a 503. `src/admin.ts` (`npm run admin -w @blackline/server -- list|create-company|reset-password`) is the only password reset (it also ends that person's sessions). The browser pane here can't register service workers, so the offline worker was not exercised on the hosted build. Not done: choosing a host, email, a scheduled clean-up of expired sessions (done at start only), shared rate-limit storage for several copies.
- Endpoints: `/auth/*`, `/me`, `/org/members`, `/audit`, `/contacts[/:id[/archive|restore|history]]`, `/jobs/:id/{enquiry,decision,award,contract,cost/...}`, `/jobs`, `/jobs/:id/{packages,estimate,parked,append,import-workbook}`, `/packages/:id/{checkout,checkin,release,break-lock}`, `/parked/:id/resolve`. `GET /jobs/:id/estimate` recalculates from checked-in records with the same engine the clients use.
- Run: `npm start -w @blackline/server` (uses vite-node; set `PORT`, and `DATA_DIR` to keep the database between runs). Smoke-tested: starts, migrates, answers `/health`.

## Web client (`packages/web`)
- Vite 5 + React 19 + AG Grid Community (grouped column headers, in-cell editing), Geist fonts, greys only. Screens: sign-in / new company, Tender Register (job list), and per job: **Estimate** (QS takeoff over resource build-up), **Packages**, **Rate Library** (add a rate as a new line in the grid; the labour true-cost builder opens as a panel under the grid), **Scope Register** (requirements with owner, treatment and a backed-up check; a register / quotes reference panel links items with one click), **Parked changes**, **Summary**. The other modules appear in the navigator as "Coming later". Every screen that edits a package uses the shared PackageBar (check out / check in / release / break, same wording everywhere).
- **The maths runs in the browser**: `src/lib/model.ts` assembles the job's records and runs `@blackline/tender/core` (the browser-safe entry; the Node-only importer is excluded), so every edit recalculates the whole job locally, as on the server. White cells are inputs, shaded cells are calculated; inputs are editable only on a package you have checked out.
- **Drafts** (`src/lib/draft.ts`, pure and tested): your edits to packages you hold, kept in `localStorage` (`bl:ws:<job>`) together with the lock version, so a refresh or a lost connection loses nothing. Check-in sends the change set; the server decides. A refused check-in clears the local draft and says the work was parked for a manager.
- **Status bar** on every screen: Online/Offline, packages checked out by you, changes waiting (black badge = needs you). Offline: the last loaded copy of the job (`bl:cache:<job>`) is shown and edits to held packages still work; checking out, checking in, releasing and breaking need a connection.
- **Commercial Review** (`lib/commercial.ts`, `screens/CommercialReview.tsx`, `PriceStack.tsx`): the CA lines edit in place (in price Yes/No, worked-out-as, rate typed as %, fixed sum), only the cells a line actually uses are white; engine-fed lines (Risk Truth, Weather, Management Reserve) show their value shaded. A margin of 100% or more is refused (it would stop the job calculating). Allowances CX01.. can be added and deleted; standard lines are switched out, never deleted. Subcontract packages (name is permanent, basis and amount edit) and the confirmed overlap sit under the lines; the price (own works + consolidated) updates live on the right. Two packages are involved (Commercial, Subcontract Packages), each with its own check-out bar.
- **Programme and Gantt** (plan and status in `docs/GANTT_PLAN.md`): two windows. *Programme* (`lib/programme.ts`, `screens/Programme.tsx`) is the tender programme (QS-linked tasks, hammock preliminaries, whole-day finish-to-start critical path) on the existing `tender/src/programme.ts`. *Gantt* is Blackline's own MS Project: engine `tender/src/gantt/` (calendars, four link types with lag, eight constraints, summaries, slack, critical path; MSPDI export/import in `mspdi.ts`; records in `records.ts`), its own checkout package "Gantt" started with `POST /jobs/:id/gantt`, editing rules in `lib/gantt.ts`, timescale in `lib/ganttView.ts`, screens `Gantt.tsx` (ribbon, state, file), `GanttTable.tsx`, `GanttChart.tsx` (SVG), `GanttInfo.tsx` (Task Information docked, not a pop-up). The file MS Project opens is MSPDI XML (`.mpp` is closed); not yet opened in MS Project itself. Gantt edits go through `commit(rows)` -> `ws.batch` (one undo step); a change that would make a loop of links is refused. Stage 2 adds three views (Gantt Chart, Resource Sheet `GanttResources.tsx`, Calendars `GanttCalendars.tsx`), 26 table columns chosen in a docked panel (`GanttColumns.tsx`, defs in `lib/ganttColumns.ts`), sort by heading and filters (`arrange()` shows summaries above matches; sorting never changes the project order), resources/assignments (`lib/ganttResources.ts`: work, cost, over-allocation) and calendar editing (`lib/ganttCalendar.ts`). A person's columns/column widths/sort/filter/zoom are kept in localStorage per job (`lib/ganttSettings.ts`), not in the project. Bar formats (`lib/ganttBars.ts`, `GanttFormat.tsx`, `GanttBarGlyph.tsx`): task `bar` > project `barStyles` by kind > `USUAL`; saved with the plan. **Programme <-> Gantt link** (`lib/programmeSync.ts` pure rules, `lib/syncDrafts.ts` applies them): a linked Gantt task has `progId` and `progSync` (the Programme's name/days/predecessors when last in step); `reconcile` does a three-way merge per field (only Programme changed: Gantt follows; only Gantt changed: Programme follows via `override_days`/`name`/`predecessors`; both: Programme wins, reported). It runs inside `workspace.commit` when `gantt:config.progLink` is set and both packages are held, so one undo reverts an edit and its knock-on; undo/redo themselves never re-sync. Structural carry (new Programme task -> Gantt task, deleted Programme task -> Gantt task removed) is in `reconcile`; deleting a linked Gantt task deletes its Programme task in the same step (`removeFromProgramme`), "Add to Programme" is `addToProgramme`. Importing an MS Project file or any rebuild without `progLink` leaves the Gantt unlinked (a notice offers "Build from the Programme and link").
- **Submission and issued revisions**: rules in `tender/src/submission.ts` (gates: blockers = scope not backed up, build-up rows with no rate/code or double-count flags, client schedule not reconciling; warnings = workbook mismatch, risk gate not PASS, minor flags, no programme; `revisionLabel` Rev A..; letter/qualification/alternative types; `submissionSeed` drafts qualifications from the register). Server: `003_revisions.sql` (`tender_revisions`, a trigger refuses any edit or delete; the only change a row takes is being superseded once), `repo/revisions.ts`, routes `POST /jobs/:id/submission`, `GET|POST /jobs/:id/revisions`, `GET /revisions/:id/records`. A revision is a full snapshot of every record plus a SHA-256 hash (shown as Unchanged / ALTERED). Issuing needs manager; refused while any package is checked out or while blockers exist, except an **owner** may issue past blockers with a written reason kept on the revision (a deliberate, audited deviation from "cannot issue"). Window `screens/Submission.tsx` (letter, qualifications, alternatives, readiness, issue, revision list, in-page compare with the previous revision or current work); edits in `lib/submission.ts`. **Letter preview and print**: "Preview and print" in the Submission window shows the letter as a page (`lib/letterDoc.ts` builds it from the letter, the switched-on qualifications and alternatives and `estimate.schedule`; `screens/LetterSheet.tsx` lays it out). Print renders the same sheet into `#print-root` and a print stylesheet hides the app; the browser's print dialog offers "Save as PDF". The preview is of work now; printing an issued revision's letter is not built, and an automatic schedule prints its "Overhead and margin" line to the client. A throwaway job "Submission test (delete me)" with a Rev A exists in the demo database; frozen revisions can't be deleted and there is no job delete yet.
- **Cost Control** (`tender/src/costControl.ts` engine, `repo/cost.ts`, `screens/CostControl.tsx` + `CostLedgers/CostVariations/CostClaims.tsx`, `lib/costWeb.ts`; migration `006_cost_control.sql`): an awarded job measured against its control budget (`GET /jobs/:id/cost` is 409 `not_awarded` otherwise). The engine is a thin layer over the QSi engine's `projectSummary` and `applyStageRetention`, so cost control uses whole cents (the TQSi full-precision chain ends where the budget is copied) and the client and server give the same totals; the server returns the raw ledger and the client runs `costControl()` (as with the estimate). **Ledgers**: `cost_commitments` (orders), `cost_actuals` (invoice/labour/plant/materials/other, a credit is negative, optional link to an order and labour hours), both **insert-only**: a trigger refuses edits and deletes, and a manager voids with a reason (kept, counts for nothing, voided once). What still counts as committed on an order is its amount less invoices booked against it (over-invoicing is an alert). **Variations** (`cost_variations`): a sell amount and cost lines (an existing code or a new one with a description); estimators propose and may edit while pending; a manager approves or rejects (reason needed to reject) and a decision freezes it (trigger). Only approved ones move the budget and contract sum, and new codes become bookable then. **Pending variations are kept out of the forecast margin** (the QSi engine would add their sell price without their cost); they are reported beside it. **Forecast** (`cost_forecasts`, insert-only, latest per code wins, history kept): "still to come" per line, blank = revised budget less spent and on order, so nothing overruns until a person says so. **Claims** (`payment_claims`, manager): value ex GST, retention % snapshotted from the contract terms at creation, GST 15% (`NZ_GST`), draft -> submitted (date) -> paid (date, amount received incl. GST); only submitted/paid claims count as claimed; voidable. **Warnings** (`engine/src/warnings.ts`, ported from QSi `commercial_control_engine.py`: `generateWarnings`, `generateVariationWarnings`, `generateClaimWarnings`, `generateProgrammeWarnings`; `costControl(ledger, {today, activities})` returns them most serious first in `warnings`, shown as "To look at" on the Cost Control summary). `today` is an argument, never the clock, so client and server agree. Cost: overrun (actual + committed past the revised budget; High past 10%), labour hours, preliminaries overrun and risk allowance 80%/100% consumed (Blackline lines are mapped onto QSi's "Preliminaries"/"Risk" types by section name and by allowance lines mentioning risk or reserve), margin drop (more than 2 points below award, Critical past 5), unallocated cost. **QSi's "Commitment Exceeds Remaining Budget" is deliberately not ported**: its `budget_remaining` is measured after the commitments, so it fires on any line bought out exactly at its budget; genuine over-commitment is the overrun rule. Variations (our records mapped onto QSi's statuses; wording uses the person's own number, V01): reply overdue (sent, `responseDue` passed), work proceeding at risk (`atRisk`), sent with no price; a decided variation has nothing to chase. Variations now carry optional `submittedOn`, `responseDue`, `atRisk` (migration `007_variation_dates.sql`). Claims: payment overdue (Critical) is the submitted date plus the contract terms' `payDays` working days, **weekends skipped, public holidays not known** (so a due date can be a day or two early); part paid when paid is less than owed. Programme: an active, non-heading Gantt task past its finish and under 100% (`activitiesOf` in `lib/costWeb.ts`). Blackline's own additions: Forecast Overrun (a line forecast over before the money is spent), Order Over-invoiced, Claimed Over Contract. Not ported because the data isn't held: notice-required/late and dispute states, EOT notices, certified/disputed claim amounts, CCA notice, retention cap, earned-value snapshots and delay events (the generators accept them; nothing feeds them yet). Undo/redo (`lib/actionHistory.ts`) covers forecasts; ledger mistakes are corrected by voiding. Not done: Xero or timesheet imports (actuals are typed in), earned value / programme tracking in the window (the QSi engine has `earnedValue`), per-line sell values (so no per-line margin), a claim document, GST on costs, a cost report/export, links from orders to Tender Procurement's selected quotes.
- **Contract Setup** (`tender/src/contract.ts` rules, `repo/contracts.ts`, `screens/ContractSetup.tsx`; migration `005_contracts.sql`): awarding a job (manager+, job status `issued`, once) from a chosen issued revision (default the current one; an earlier one is allowed because the client may have accepted it; a revision whose hash no longer matches is refused). The award **copies the estimate's cost into the control budget**: one line per QS item, pre-margin allowance (CA01-CA16) and subcontract package, which add up to the estimate's `grossKnownPackage`; each line rounded to the cent at copy. Cost codes are the estimate's own (QS code, CA ref, `SUB-01..`); one standard across jobs is still an open decision. The **margin** (overhead, bonds, finance, profit) is the contract sum less the budget and is not a budget line. Tables `contracts` (revision, contract sum, tender all-in, terms jsonb, awarded on/by) and `contract_budget_lines`, whose rows a trigger refuses to edit or delete (changes after award will be variations). The contract sum defaults to the tender all-in unless the client agreed another. Terms (form NZS 3910:2023/2013, 3915, 3916, subcontract agreement, PO/letter of intent, other; contract/client ref, start, practical completion, claim day, payment days, retention %, defects months, LDs per day, notes) are checked by `cleanTerms`, edited by a manager after award, and audited from/to. After award the job is `awarded` and `issueRevision` refuses (`awarded`). Window: before award, pick the revision, see the budget it would copy, award with an in-page confirm; after, the budget by section, terms (autosave with undo/redo, `lib/actionHistory.ts`) and "Download as CSV". Not done: variations (the next module, Cost Control), withdrawing an award, a contract document, linking budget lines to quotes/subcontract orders, a Xero export.
- **Tender Procurement** (`tender/src/procurement.ts` rules, `screens/TenderProcurement.tsx`, `lib/procurement.ts` edits): its own package "Tender Procurement" (`POST /jobs/:id/procurement` makes one package per distinct `package` name in the quote register, linked to the subcontract package (overlay) of the same name when there is one). A package's quotes are the quote-register entries whose `package` matches its name; the quotes themselves stay in the quote register (Scope Register), not copied. **Invites** (`procInvite`: who was asked, sent, due, waiting/quoted/declined/no response; supplier typed or picked from Contacts). **Levelling** per quote (`procLevel`, keyed by the quote ref): adjustments (a saving may be negative) so the levelled total = quoted + adjustments, to the cent, and each stated exclusion given a treatment (priced in the adjustments, own works, by others, accepted risk). Quotes are ranked by levelled total (equal totals share a place). **Adjudication**: a person selects one quote with a reason (kept with who and when); the platform never selects. A selected quote with an exclusion not dealt with, no amount, or no longer in the register is a **blocker in `submission.gates`**; packages with quotes and none selected, and a selected quote that differs from the linked overlay's amount, are warnings. The estimate's money is never changed by procurement: the difference is shown and the overlay is edited in Commercial Review. `computeTenderEstimate` returns `procurement`. Quote validity is shown in the window against today's date but is deliberately not part of the estimate (a recalculation must not depend on the date). Not done: sending the enquiry out (email), importing a quote, per-line quote comparison, supplier quotes for materials against QS items, a procurement report.
- **Tender Documents** (`tender/src/documents.ts` rules, `screens/TenderDocuments.tsx`, `lib/documents.ts` edits): its own package "Tender Documents" (`POST /jobs/:id/documents` starts it from the register's document items, each becoming the first revision of a `tenderDoc` / `tenderDocRev`; same refs, so scope links still work). Revisions are only added (latest is current; the latest can be deleted to correct a mistake). **Every revision after a document's first raises flags**, one per thing that depends on it: scope items citing the document's ref in `register_refs`, the estimate lines those items carry (`cost_refs`), and quotes (listed in a cited scope item's `quote_refs`, or naming the ref in their `documents` text). A document nothing cites raises one "nothing says what this touches" flag instead. A flag stays open until someone clears it with a note (`tenderDocClear`, by name and date; re-openable), and **open flags are a blocker in `submission.gates`** (owner override with reason, like the other blockers). `computeTenderEstimate` returns `documents` (documents with revisions, flags, addenda grouped by the revision's `addendum` text, gate). RFIs stay in the register (Scope Register); the window shows the open count. Known duplication to resolve: documents still also exist as register items (`kind: document`); the seeded revision label is the register's first detail line, which for Hobsonville is sometimes a file name. Not done: file upload or a PDF viewer, linking a revision to RFIs, flagging programme tasks, a separate addenda record (an addendum is just the text on a revision).
- **Contacts and Enquiries** (company-wide, page `#/contacts/enquiries|contacts`, not per job; `screens/ContactsPage.tsx` holds the data, undo/redo and tabs). *Enquiry register* (`EnquiryRegister.tsx`, `lib/enquiries.ts`): the enquiry is the job record itself, so the register fields live on `jobs` (`contact_id`, `owner_id`, `due_at`, `notes`, `approx_value`, `decision_reason`; migration `004_contacts.sql`). Open work is ordered by deadline; a deadline is a calendar date stored as midnight UTC and read back with `dueDate()` so no time zone moves it. Go/no-go (`repo/enquiries.ts decide`, manager+): **go** needs an owner and a deadline (enquiry -> tendering), **no-bid** and **lost** need a reason, kept in `decision_reason` and the audit trail, **reopen** brings a no bid or lost one back. Award is for Contract Setup. Jobs can't be deleted. *Contacts* (`ContactList.tsx`, `repo/contacts.ts`): clients, consultants, subcontractors, suppliers; one entry per company and kind; estimators edit; archive/restore instead of delete; every edit keeps the earlier value in `contact_history` (latest edit wins). A job's client shown is the linked contact's current name. These screens save as you edit (no checkout), so undo/redo (`lib/actionHistory.ts`) saves the earlier value back. Not done: several people per company, a place to record a contact's documents or quotes, linking quotes/suppliers to contacts (comes with Tender Procurement).
- **Undo / redo** (`lib/history.ts`, in `workspace.ts`): each change to the drafts remembers the drafts before it (up to 200 steps, in memory). Buttons in the PackageBar and Ctrl+Z / Ctrl+Y (not while typing in a box). History is cleared when a package is checked in or released, so an undo can never bring back drafts of a package that is no longer yours. All draft changes must go through `commit` in the workspace.
- **QS items** (`lib/qs.ts`): "Add item" opens a new takeoff line in the section of the selected item (same package, so already held); description, unit and quantity edit in place. "Delete item" removes the item and its build-up rows as one undoable step (`removeMany`), asking first in the page bar when it has rows. New sections are added with "New section" (see below).
- **No pop-ups**: nothing opens over the work. Adding a rate or requirement is a pinned new line in the grid (code/requirement cell opens, then the next cell); questions (release, break lock) are a bar above the grid (`ConfirmBar`); notices are in-page bars. Do not use `window.confirm/prompt/alert`.
- **Labour builder** (`lib/labour.ts`, `screens/LabourBuilder.tsx`): percentages typed as %, engine takes fractions; live build-up from `computeLabourRate`; save writes `library:<CODE>` (Labour, hr, price/wording/source from the build) and `labour:<CODE>` (`{inputs, history}`) into the Rate Library package. A rate typed in by hand is never overwritten; built rates cannot be deleted; a rebuild keeps a note of the earlier rate/status/evidence in `history`.
- **Scope Register** (`lib/scope.ts`, `screens/Scope.tsx`): edits go through `scope.setField`/`buildItem` from the tender package; status, gate and unhomed QS items come from `estimate.scope`. Register items and quotes (`lib/registers.ts`, `screens/References.tsx`) edit in place the same way: add line, edit cells, delete, and link to the selected requirement.
- **Excel and PDF files** (`tender/src/outputs/estimateWorkbook.ts` ExcelJS, `outputs/letterPdf.ts` PDFKit with built-in Helvetica, both Node-only so exported from `index.ts` not `core.ts`; `repo/exports.ts`; `screens/DownloadButton.tsx`, `api.ts apiDownload`). Written server-side from the engine's own estimate (nothing recalculated in the writer), for the **job as checked in** or for an **issued revision exactly as sent** (from its frozen snapshot; the PDF is dated the day it was issued). Routes: `GET /jobs/:id/export/{estimate.xlsx,letter.pdf}` and `GET /revisions/:id/export/{estimate.xlsx,letter.pdf}`; anyone in the company can download; the letter is 409 `no_letter` until the Submission has been started. The workbook has Summary, QS Takeoff, Build-up, Commercial, Price schedule, Subcontracts, Scope, Quotes, and Procurement once started; money cells are cents-rounded numbers (a cell is a double: the file is for reading and checking, the platform holds the exact figures); the Hobsonville golden test checks the file's all-in is 1,226,916.81. The letter's content is built once in `tender/src/letter.ts` (`letterDoc`) and used by the on-screen preview, the print and the PDF, so they can't disagree. Buttons: Summary ("Download as Excel"), Submission (live letter "Download PDF"; "Excel" and "Letter PDF" on every revision). A qualification drafted from the register now uses the item's full `detail` when the 300-character title is only the start of it (older submissions keep the text they were drafted with). Not done: a PDF of the estimate or price schedule on its own, a branded letterhead or logo, PDF of the contract budget or cost report, emailing a file.
- **Starting a tender and QS sections** (`tender/src/template.ts`, `screens/StartTender.tsx`; routes `POST /jobs/:id/template`, `POST /jobs/:id/sections`): a job with no packages shows "Start this tender" on the Estimate screen: **blank** (estimator+: the standard commercial stack CA01-CA24 with the workbook's wording, only risk (CA01/02, which cost nothing until exposures exist), overhead and profit switched on, the overhead % and margin % typed on the panel (10 and 15 offered as starting points; margin is capped at 60% so the stack can't stop calculating), the packages every tender is built from, no sections) or **import a workbook** (manager, `POST /jobs/:id/import-workbook`, file upload in `api.ts apiUpload`). Both refuse a job that already has packages. A **QS section** is a package of its own (`qs:<name>`, name tidied and unique ignoring capitals; "Unassigned rows" is reserved), added with "New section" beside the Section picker; the creator holds it straight away. "Add item" goes into the section chosen in the picker (default: the selected item's), and empty sections show as rows. Not done: copying a rate library from another job or the company (a blank tender starts with an empty Rate Library), renaming or deleting a section, moving an item between sections.
- **What the workbook importer reads beyond the core sheets**: a **Scope Coverage** sheet when there is one (`scopeFromSheet`: header row, "Requirement" is the one needed column, headers may carry a bracketed hint; each row goes through the scope builder, and a row whose group, owner or treatment isn't one of ours is **kept with those three blank** to be set on screen rather than dropped), and the **MS Project Import** table as the programme when the workbook has no usable Programme Export (`programmeFromMsImport`: ID, WBS = QS code, Task Name, Duration as days/weeks/hours rounded up, Predecessors as task IDs, "4FS"/"4SS+2d" read as task 4, finish-to-start only). Both report in the import notes. A build-up row with a code but no recognised calculation now **stops the import naming the row** (the engine can't price it).
